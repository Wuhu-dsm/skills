# 全栈项目学习工作流

## 核心原则

默认先只读探索，不要急着改代码，除非用户明确要求实现。

目标不是总结每个文件，而是快速弄清楚：
- 项目如何启动
- 请求如何流转
- 业务逻辑在哪里
- 前后端契约如何维护
- 数据如何建模和持久化
- 修改代码时应该遵守什么约定
- 如何验证改动是安全的

所有结论都要尽量引用具体文件路径。

## 阶段 1：仓库初步判断

优先查看：

- `README.md`
- `AGENTS.md`
- `package.json`
- `pnpm-workspace.yaml`
- `turbo.json`
- `go.mod`
- `pyproject.toml`
- `pom.xml`
- `build.gradle`
- `docker-compose.yml`
- `.env.example`
- `Makefile`
- `.github/workflows`
- `apps/`
- `packages/`
- `frontend/`
- `backend/`
- `services/`
- `cmd/`
- `internal/`
- `migrations/`
- `prisma/`
- `schema/`

需要回答：

1. 这是 monorepo、模块化单体，还是单服务项目？
2. 主要应用或服务有哪些？
3. 使用了什么包管理器和构建系统？
4. 项目推荐的启动、测试、构建命令是什么？
5. 本地环境依赖由哪些文件定义？

## 阶段 2：建立系统地图

输出一份简洁的架构地图。

### 前端

识别：
- 应用入口
- 路由
- 页面和布局
- 组件结构
- 状态管理
- API client
- 表单校验
- 样式系统
- 测试配置

### 后端

识别：
- 服务入口
- 配置加载
- 路由注册
- 中间件
- handler/controller
- service/usecase
- repository/DAO
- 认证和权限
- 后台任务
- 错误处理
- 日志和链路追踪

### 数据层

识别：
- 数据库类型
- ORM 或查询层
- schema/migration
- seed 数据
- 核心实体
- 事务模式

### 基础设施

识别：
- 本地开发依赖
- Docker/dev container
- CI 命令
- 部署配置
- 环境变量
- 可观测性配置

## 阶段 3：生成本地运行指南

如果用户想跑项目，推导最安全的本地启动路径。

输出：

1. 前置依赖
2. 必要环境变量
3. 是否需要数据库、Redis、消息队列等本地服务
4. 安装依赖命令
5. migration/seed 命令
6. 前端启动命令
7. 后端启动命令
8. test/typecheck/lint/build 命令
9. 常见失败点

优先使用项目已有命令，例如 `README.md`、`Makefile`、`package.json`、CI 中定义的命令。

不要编造密钥或环境变量值。

## 阶段 4：追踪一条端到端业务链路

全栈项目优先纵向追业务流，而不是横向读目录。

如果用户没有指定功能，优先选择：
- 登录/认证
- 创建订单/文章/资源
- 列表/搜索
- 支付/结算
- 文件上传
- 管理后台 CRUD

追踪内容：

1. 前端页面或组件
2. 用户事件处理函数
3. 前端校验逻辑
4. API client 调用
5. 请求和响应类型
6. 后端路由
7. 中间件和认证
8. handler/controller
9. service/usecase
10. repository/数据库查询
11. 事务、缓存、队列逻辑
12. 响应数据如何映射
13. 前端状态或缓存如何更新
14. loading/error/empty 状态
15. 相关测试

必要时用 Mermaid 画调用链图。

## 阶段 5：总结项目约定

总结贡献者必须遵守的约定：

- 命名规范
- 目录边界
- 业务逻辑应该放在哪里
- 如何新增 API
- 如何修改数据库
- 错误如何表示
- 测试如何组织
- 前后端共享类型或契约如何维护
- 认证和权限如何执行

要区分“文件中已确认的事实”和“基于代码结构的合理推断”。

## 阶段 6：设计学习练习

推荐 3 到 5 个小任务，按难度排序。

每个任务说明：

- 要改什么
- 涉及哪些前端文件
- 涉及哪些后端文件
- 是否影响数据库
- 能学到什么
- 如何验证
- 风险等级

优先选择低风险任务：
- 增加 loading/empty/error 状态
- 给列表页加筛选条件
- 给已有表单加校验
- 给已有接口增加一个返回字段
- 补后端测试
- 增加健康检查接口
- 文档化一个 API 契约
- 改善某条路径的错误处理

## 阶段 7：改代码前

改代码前先给计划：

1. 目标
2. 可能涉及的文件
3. 需要遵守的现有模式
4. 风险点
5. 验证命令
6. 回退考虑

只有在用户明确批准或要求实现后才开始编辑。

## 阶段 8：改代码后

实现后：

1. 先跑最相关的小范围测试
2. 如果影响共享逻辑，再跑更广的验证
3. 总结修改过的文件
4. 解释为什么这些改动符合项目现有模式
5. 说明剩余风险或未覆盖测试

Go 项目可考虑：

- `go test ./...`
- `go test -race ./...`
- `go vet ./...`

Node/TypeScript 项目可考虑：

- 项目自己的 test 命令
- `typecheck`
- `lint`
- `build`

优先使用仓库或 CI 中已有的命令。

## 输出模板

### 仓库地图

```text
项目类型：
技术栈：
主要应用/服务：
本地启动路径：
重要目录：
优先学习的核心链路：
推荐阅读顺序：
```

### 功能链路追踪

```text
功能：
前端入口：
API 调用：
后端路由：
业务逻辑：
数据访问：
数据库表/实体：
认证和权限：
相关测试：
学习重点：
```

### 学习计划

```text
第 1 天：跑通项目并绘制架构地图
第 2 天：追踪认证或核心功能链路
第 3 天：研究数据模型和 API 契约
第 4 天：做一个小的前端相关改动
第 5 天：做一个小的后端或数据层改动
第 6 天：补充或改进测试
第 7 天：复盘架构并整理学习笔记
```

## 质量标准

一个好的输出应该：

- 避免空泛的架构判断
- 引用具体文件路径
- 区分事实和推断
- 给出实用的阅读顺序
- 优先追踪端到端业务流
- 避免过早重构
- 把学习转化为小而可验证的练习
